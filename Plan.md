# План автоматизации тестирования

## Цель проверки

Проверить покупку тура в учебном приложении двумя способами: оплата дебетовой картой и покупка в кредит. Для успешных и отклонённых ответов банка сверить уведомление приложения и запись в базе данных. Отдельно проверить валидацию каждого поля формы. Полный набор сценариев выполняется с MySQL и PostgreSQL.

Поля формы: номер карты, месяц действия, год действия, имя владельца и код безопасности карты. Набор полей одинаков для способов оплаты **Купить** и **Купить в кредит**.

## Тестовые данные

Для успешных сценариев и проверок валидации используется базовый набор валидных данных одобряемой карты:

- номер одобряемой симулятором карты: `4444 4444 4444 4441`;
- месяц и год действия: `12` и `30`;
- имя владельца: `IVAN IVANOV`;
- код безопасности карты: `123`.

Для сценариев отказа используется базовый набор валидных данных отклоняемой карты: номер `4444 4444 4444 4442`, срок действия `12/30`, имя владельца `IVAN IVANOV`, код безопасности `123`.

Сумма тура в приложении составляет 45 000 рублей. В таблице `payment_entity` ожидается сумма `4500000` в минимальных единицах валюты.

В каждом сценарии проверки валидации базовый набор одобряемой карты используется для всех полей, кроме поля, значение которого изменяется в этом сценарии. Каждый сценарий проверки валидации выполняется отдельно для способов **Купить** и **Купить в кредит**, а также для конфигураций MySQL и PostgreSQL. Если в сценарии проверяется пустое поле, остальные четыре поля заполняются валидными данными.

Для проверки длины имени владельца принято рабочее предположение: разрешены латинские буквы, пробел и дефис, длина от 2 до 50 символов. Учебное задание не устанавливает точные границы. До закрепления этого ожидания в автоматизированном тесте его следует согласовать с преподавателем.

## Проверки базы данных

Для каждого сценария покупки проверяются записи, созданные именно текущим запуском: идентификаторы существующих операций фиксируются до отправки формы. Для дебетовой оплаты проверяются статус и сумма записи в `payment_entity`, а также связь записи с заказом. Для покупки в кредит проверяются статус записи в `credit_request_entity` и связь с заказом. После успешных и отклонённых операций подтверждается отсутствие сохранённых реквизитов карты. Для сценариев валидации проверяется отсутствие новой успешной операции и соответствующей записи о платеже или кредитной заявке.

Сценарии покупки и проверки отсутствия записей выполняются сначала с MySQL, затем с PostgreSQL. Результат отказа сопоставляется с уведомлением приложения и статусом в базе данных.

## Инструменты

- Java 11 и Gradle Wrapper — язык и повторяемый запуск проекта без отдельной установки Gradle.
- JUnit 5 — запуск отдельных тестовых сценариев и подготовка/завершение проверок.
- Selenide и удалённый Chrome через Selenium Grid — взаимодействие с приложением в браузере без зависимости от локально установленного браузера.
- JDBC и драйверы MySQL/PostgreSQL — чтение статусов и суммы после действий в интерфейсе.
- Allure — отображение шагов, скриншотов и диагностики ошибок.
- Docker Compose — запуск двух систем управления базами данных и банковского симулятора в одинаковом окружении.

## Возможные проблемы

- Приложение может показать успешный результат при отказе банка. Уведомление интерфейса и статус в базе проверяются независимо; при расхождении сохраняется скриншот и создаётся сообщение о дефекте. Известный случай описан в `issues/BUG-001-decline-shown-as-approved.md`.
- Банковский симулятор возвращает код `400` для карты, которой нет в `data.json`. В сценарии 05 ожидается отказ без успешного статуса; статус `DECLINED` не требуется, если симулятор его не вернул.
- Проверки даты зависят от текущего календаря. Прошлая дата и дата более чем через шесть лет рассчитываются относительно даты запуска; примеры в плане приведены для 09.10.2026.
- Маска поля может отфильтровать символы до отправки формы. Проверяется итоговое содержимое поля и отсутствие операции, а не только возможность набрать символ.
- MySQL и PostgreSQL могут различаться представлением денежных значений и сортировкой записей. Для поиска используются новые идентификаторы операций; одинаковые проверки выполняются отдельно для каждой системы.
- Selenium Grid, приложение или банковский симулятор могут быть недоступны. Перед прогоном проверяется готовность сервисов; техническая ошибка соединения не трактуется как дефект бизнес-логики.
- Учебное задание не определяет допустимую длину имени и запрет нулевого кода безопасности. Эти критерии согласуются с преподавателем до фиксации соответствующих ожидаемых результатов.

## Оценка и сроки

Оценка с учётом повторных прогонов на двух системах управления базами данных: анализ приложения и схемы базы — 2–3 часа; тест-дизайн и подготовка данных — 3–4 часа; автоматизация сценариев покупки и проверки формы — 9–13 часов; настройка окружения и прогоны — 3–5 часов; разбор дефектов и итоговые документы — 2–3 часа. **Итого: 19–28 часов.**

План сдачи: день 1 — утверждение сценариев, подготовка окружения и тестовых данных; день 2 — автоматизация сценариев 01–05 и проверок базы; день 3 — автоматизация сценариев 06–25; день 4 — прогоны на MySQL и PostgreSQL, регистрация дефектов, подготовка отчёта о тестировании и итогов автоматизации.
