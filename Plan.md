# План автоматизации тестирования

## Цель проверки

Проверить оплату тура дебетовой картой и покупку в кредит, обработку ответа банковского симулятора, запись результата в базу данных и валидацию полей платежной формы. Каждый тестовый сценарий проверяет один способ покупки и одно значение поля. Сценарии запускаются отдельно с MySQL и PostgreSQL.

## Общие данные

Базовые валидные данные одобряемой карты: номер `4444 4444 4444 4441`, месяц `12`, год `30`, владелец `IVAN IVANOV`, код безопасности `123`.

Базовые валидные данные отклоняемой карты: номер `4444 4444 4444 4442`, месяц `12`, год `30`, владелец `IVAN IVANOV`, код безопасности `123`.

Сумма тура — 45 000 рублей; в `payment_entity` ожидается `4500000` в минимальных единицах валюты. В сценариях проверки полей остальные значения соответствуют базовым валидным данным одобряемой карты. Для длины имени владельца принято рабочее ограничение от 2 до 50 символов.

## Проверки базы данных

Перед отправкой формы фиксируются идентификаторы существующих операций. Для дебетовой оплаты проверяются статус, сумма и связь записи `payment_entity` с заказом. Для покупки в кредит проверяются статус записи `credit_request_entity` и связь с заказом. Для проверок валидации подтверждается отсутствие новой операции. Реквизиты карт не должны сохраняться в базе.

## Инструменты

- Java 11 и Gradle Wrapper — запуск проекта без отдельной установки Gradle.
- JUnit 5 и Selenide — раздельные автоматизированные проверки интерфейса.
- Удалённый Chrome через Selenium Grid — запуск браузера вне локальной системы.
- JDBC — чтение результатов операций в MySQL и PostgreSQL.
- Allure — отчёт о шагах и ошибках тестов.
- Docker Compose — запуск баз данных и банковского симулятора.

## Возможные проблемы

- При отказе банка интерфейс может показать успех; уведомление сверяется со статусом в базе. Известный дефект описан в `issues/BUG-001-decline-shown-as-approved.md`.
- Для неизвестной карты симулятор отвечает кодом `400`; ожидается отсутствие успешной операции.
- Срок действия карты зависит от календарной даты; граничные даты формируются относительно дня запуска.
- Маска формы может изменить введённые символы; проверяется итоговое значение поля.
- Перед прогоном проверяется доступность приложения, Selenium Grid, баз данных и симулятора.
- Точные границы длины имени и правило для кода безопасности `000` следует согласовать с преподавателем.

## Оценка и сроки

Оценка: анализ приложения и базы данных — 2–3 часа; подготовка тестовых данных и автоматизация 25 сценариев — 12–17 часов; настройка среды и прогоны на двух базах данных — 3–5 часов; анализ дефектов и подготовка отчётов — 2–3 часа. **Итого: 19–28 часов.**

План сдачи: день 1 — подготовка среды и тестовых данных; дни 2–3 — автоматизация сценариев 01–25; день 4 — прогоны на MySQL и PostgreSQL, регистрация дефектов и подготовка отчётов.
