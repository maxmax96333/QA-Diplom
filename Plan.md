# План автоматизации тестирования

## Цель и границы проверки

Проверить покупку тура в учебном приложении двумя способами: оплатой дебетовой картой и покупкой в кредит. Сопоставить уведомления приложения с результатами в базе данных. Проверить валидацию каждого поля формы.

Один тестовый сценарий проверяет один способ покупки и одно значение проверяемого поля. Каждому сценарию соответствует отдельный автотест. Проверки отдельно повторяются для MySQL и PostgreSQL. Поля формы: номер карты, месяц и год действия, имя владельца, код безопасности карты. Способы покупки в интерфейсе: **Купить** и **Купить в кредит**.

## Общие тестовые данные

Базовые валидные данные одобряемой симулятором карты: номер `4444 4444 4444 4441`, месяц действия `12`, год действия `30`, имя владельца `IVAN IVANOV`, код безопасности `123`.

Базовые валидные данные отклоняемой симулятором карты: номер `4444 4444 4444 4442`, месяц действия `12`, год действия `30`, имя владельца `IVAN IVANOV`, код безопасности `123`.

Сумма тура — 45 000 рублей. В `payment_entity` ожидается сумма `4500000` в минимальных единицах валюты.

В сценариях проверки полей все значения берутся из базового набора одобряемой карты; меняется только значение, указанное в данных конкретного сценария. Для проверки длины имени владельца принято рабочее предположение: разрешены латинские буквы, пробел и дефис, допустимая длина составляет от 2 до 50 символов. Это предположение необходимо согласовать с преподавателем, поскольку задание не устанавливает точные границы.

### Тестовый сценарий 01. Проверка успешной дебетовой оплаты в приложении после отправки формы
**Данные:** базовые валидные данные одобряемой карты; способ покупки **Купить**.
**Шаги:** открыть приложение; выбрать **Купить**; заполнить форму; отправить её.
**Ожидаемый результат:** приложение показывает уведомление об успешной операции. В `payment_entity` появляется запись со статусом `APPROVED` и суммой `4500000`; заказ связан с записью. Реквизиты карты в базе не сохраняются.

## Проверки базы данных

До отправки каждой формы фиксируются идентификаторы существующих операций. После дебетовой оплаты проверяются статус и сумма записи в `payment_entity`, а также связь записи с заказом. После покупки в кредит проверяются статус записи в `credit_request_entity` и связь с заказом. Для успешных и отклонённых операций подтверждается отсутствие сохранённых реквизитов карты. Для проверок валидации подтверждается отсутствие новой записи об операции.

Каждый тест выполняется отдельно с MySQL и PostgreSQL. Для отказных сценариев текст уведомления сопоставляется со статусом в базе данных.

## Инструменты

- Java 11 и Gradle Wrapper — язык и запуск проекта без отдельной установки Gradle.
- JUnit 5 — отдельный запуск каждого тестового сценария.
- Selenide и удалённый Chrome через Selenium Grid — взаимодействие с приложением в браузере без локально установленного браузера.
- JDBC и драйверы MySQL/PostgreSQL — проверка результатов операций в базе данных.
- Allure — отчёт о шагах, скриншотах и ошибках тестов.
- Docker Compose — запуск двух систем управления базами данных и банковского симулятора в одинаковом окружении.

## Возможные проблемы

- Приложение может показать уведомление об успехе при отказе банка. Для каждого отказного сценария результат интерфейса и статус в базе проверяются независимо. Известный дефект описан в `issues/BUG-001-decline-shown-as-approved.md`.
- Банковский симулятор возвращает код `400` для карты, отсутствующей в `data.json`. В сценариях 05 и 06 ожидается отказ и отсутствие успешного статуса.
- Проверки срока действия зависят от даты запуска. Предыдущий месяц и срок более чем через шесть лет вычисляются относительно даты выполнения; примеры приведены для 11.10.2026.
- Маска поля может отфильтровать ввод до отправки формы. Проверяется итоговое значение поля и невозможность выполнить операцию с некорректными данными.
- Результаты и типы денежных значений могут различаться между MySQL и PostgreSQL. Сценарии запускаются отдельно на каждой системе; для поиска новых записей используются идентификаторы операций.
- При недоступности Selenium Grid, приложения или симулятора тест не проверяет бизнес-результат. Перед прогоном проверяется готовность сервисов.
- Учебное задание не устанавливает допустимую длину имени и ограничение на нулевой код безопасности. Эти правила необходимо согласовать с преподавателем до окончательной фиксации ожиданий.

## Оценка и сроки

Оценка с учётом отдельных тестов для двух способов покупки и повторных прогонов на двух системах управления базами данных: анализ приложения и схемы базы — 2–3 часа; тест-дизайн и тестовые данные — 4–6 часов; автоматизация 72 сценариев — 14–20 часов; настройка окружения и прогоны — 4–6 часов; анализ дефектов и отчётные документы — 2–4 часа. **Итого: 26–39 часов.**

План сдачи: день 1 — согласование ожидаемых результатов, настройка окружения и подготовка тестовых данных; день 2 — автоматизация сценариев 01–14; день 3 — автоматизация сценариев 15–40; день 4 — автоматизация сценариев 41–60; день 5 — автоматизация сценариев 61–72, отдельные прогоны на MySQL и PostgreSQL, регистрация дефектов и подготовка отчётных документов.
